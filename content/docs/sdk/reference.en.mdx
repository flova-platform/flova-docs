Use this reference for device firmware and Linux applications. Examples are C++11 fragments unless marked as a complete sketch. Use the exact, case-sensitive technical keys and value types in your published Device Type. Keep the device, any injected services, and callback contexts alive for as long as the SDK uses them.

## Complete Arduino sketch

Publish a writable Boolean stream named `relay` and a Number (`double`) stream named `temperature`. This ESP32 sketch drives an active-high LED on GPIO2 and reports a simulated temperature every five seconds. On other boards, choose a suitable pin and [device type](#choose-a-device-type).

```cpp
#include <Arduino.h>
#include <FlovaSDK.h>

FlovaEsp32 device;
auto relay = FLOVA_DATASTREAM(device, bool, "relay");
auto temperature = FLOVA_DATASTREAM(device, double, "temperature");
bool started = false;

flova::WriteResult setRelay(bool enabled) {
  digitalWrite(2, enabled ? HIGH : LOW);
  return flova::accept();
}

void setup() {
  Serial.begin(115200);
  pinMode(2, OUTPUT);
  digitalWrite(2, LOW);
  temperature.mode(flova::Mode::Sample);
  if (!relay.tryOnWrite(setRelay)) {
    Serial.println("Could not register relay");
    return;
  }
  started = device.begin();
  if (!started) Serial.println(device.lastError());
}

void loop() {
  if (!started) return;
  device.run();
  static unsigned long lastSample = 0;
  const unsigned long now = millis();
  if (now - lastSample < 5000) return;
  lastSample = now;
  const auto result = FLOVA_REPORT(temperature, 23.4);
  if (!result.accepted()) Serial.println(result.reason);
}
```

## Datastream helpers

### `FLOVA_DATASTREAM`

`FLOVA_DATASTREAM(device, T, key)` calls `device.stream<T>(key)`. Use `bool`, `int64_t`, `float`, `double`, or `flova::Text` for `T`. On managed ESP and Linux, constructing the helper does not register a descriptor or touch storage until first use. Direct typed handles resolve when requested. Register handlers and configure policies before [`begin()`](#begin) so the runtime can bind those declarations.

```cpp
auto count = FLOVA_DATASTREAM(device, int64_t, "count");
auto label = device.stream<flova::Text>("label");
auto relayHandle = device.datastream<bool>("relay"); // ESP or portable Device
```

Linux uses `stream<T>()` or `flovaDatastream<T>()`; Universal ESP32 BLE uses `device.device().datastream<T>()`. The lazy wrapper's `key()` returns the declaration key (keep the key string alive); the typed handle offers [`valid()`, `bound()`, and `snapshot()`](#typed-handle-inspection).

### `FLOVA_WRITE`

`FLOVA_WRITE(relay, value)` calls `relay.write(value)` and returns a [`WriteResult`](#writeresult). It validates the value and calls the hardware handler synchronously with local-logic origin. A rejection leaves authoritative state unchanged; a value already applied can return `NoChange` without calling the handler. Sample and Event streams do not accept writes.

```cpp
const auto result = FLOVA_WRITE(relay, false); // same as relay.write(false)
if (!result.accepted()) Serial.println(result.reason);
```

### `FLOVA_REPORT`

`FLOVA_REPORT(stream, value[, origin])` calls `stream.report(value, origin)`. It records an observation without invoking the write handler. The default origin is `flova::Origin::SensorRead`; pass `PhysicalInput` for physical feedback. Local acceptance is not a delivery acknowledgement, and offline policy can discard or reject a report.

```cpp
const auto sample = FLOVA_REPORT(temperature, 23.4);
// feedbackPin is a separate input configured by the application.
const auto feedback = FLOVA_REPORT(relay, digitalRead(feedbackPin) == HIGH,
                                  flova::Origin::PhysicalInput);
if (!sample.accepted()) Serial.println(sample.reason);
if (!feedback.accepted()) Serial.println(feedback.reason);
```

### `FLOVA_HAS_VALUE`

`FLOVA_HAS_VALUE(stream)` calls `stream.hasValue()`. It returns whether there is a local value, not whether it is fresh, synchronized, or physically confirmed.

```cpp
if (!FLOVA_HAS_VALUE(temperature)) Serial.println("No sample yet");
```

### `FLOVA_READ`

`FLOVA_READ(stream)` calls `stream.value()`. It returns the cached value, not a hardware reading or a cloud request. Without a value it returns `T()` (for example `false`, zero, or empty text); use [`FLOVA_HAS_VALUE`](#flova_has_value) to distinguish absence.

```cpp
if (FLOVA_HAS_VALUE(relay)) {
  const bool cached = FLOVA_READ(relay);
  Serial.println(cached ? "on" : "off");
}
```

### `FLOVA_ON_WRITE`

`FLOVA_ON_WRITE(stream, handler[, context])` calls `stream.onWrite(...)`, which returns the stream for chaining, not a success flag. Use `tryOnWrite(...)` when failure to register matters. Both accept a function taking `T`, or a function taking `(void*, T)` plus a context pointer. Return `flova::WriteResult` if hardware can refuse the action; a `void` handler is treated as acceptance. Remote handlers run from `run()`. Keep them short and validate before changing hardware.

```cpp
FLOVA_ON_WRITE(relay, setRelay);                  // same as relay.onWrite(setRelay)
if (!relay.tryOnWrite(setRelay)) return;          // in setup(), instead of the line above
```

```cpp
uint8_t relayPin = 2; // Set pinMode before registration; keep this context alive.
auto applyOutput = [](void* context, bool on) -> flova::WriteResult {
  const auto pin = *static_cast<uint8_t*>(context);
  digitalWrite(pin, on ? HIGH : LOW);
  return flova::accept();
};
// In setup(), as an alternative handler:
// if (!relay.tryOnWrite(applyOutput, &relayPin)) return;
```

### `FLOVA_SETTING`

`FLOVA_SETTING(device, T, key, fallback)` calls `device.setting<T>(key, fallback)`. Declare it before `begin()` on ESP facades exposing `setting()`, `FlovaClient`, or portable `Device`. It registers a local fallback, then reads the applied configuration as it changes. `Setting<T>::valid()` checks registration; `hasValue()` is true even for a valid fallback; `value()` returns the local value or `T()` without one. It never requests configuration from the network.

```cpp
auto threshold = FLOVA_SETTING(device, double, "threshold", 35.0);
// Equivalent: auto threshold = device.setting<double>("threshold", 35.0);
if (threshold.valid() && threshold.hasValue()) Serial.println(threshold.value());
```

See [Configuration and settings](../configuration/) for validating values before applying them to hardware.

## Custom log events

### `FLOVA_LOG_EVENT`

```cpp
bool logEvent(const char* code, const char* message = "");
```

`FLOVA_LOG_EVENT(device, code[, message])` forwards to `device.logEvent()` and
returns the same `bool`. Use it on `FlovaEsp32`, `FlovaEsp8266`, `FlovaEsp32Ble`,
`FlovaEsp32Ethernet`, or `FlovaClient` with a Link that implements log event
delivery. It is not part of `FlovaLinux` or the portable `flova::Device` API.

- **Code:** 1–32 ASCII bytes. Start with a lowercase letter; use only lowercase
  letters, digits, and underscores after it. Codes need no registration.
- **Message:** optional, up to 96 UTF-8 **bytes**, not characters. Do not include
  credentials, secrets, or other sensitive data.
- **Result:** `true` means the SDK copied the event into its one-entry RAM queue,
  not that Engine stored it. `false` means invalid input, the client has not
  started or has failed, or the queue is full. Call from application code after
  `begin()` succeeds, never from an interrupt handler.

Continue calling `run()` even when disconnected. The SDK retries the pending event
until Engine acknowledges or rejects it. Engine deduplicates retries. A reboot
discards the pending event; it is not written to device storage. If your code
receives `false`, keep running the device loop and decide whether to retry later
or skip that event.

```cpp
device.logEvent("sensor_fault");
FLOVA_LOG_EVENT(device, "temperature_high", "Temperature exceeded 80 C");
```

Follow the [Log Event tutorial](../log-event/) to verify delivery in Console.

## Typed handle inspection

`valid()`, `bound()`, and `snapshot()` belong to `flova::Datastream<T>`, not the lazy `FlovaDatastream<T, Client>` wrapper. `key()` belongs to the lazy wrapper.

| Method                      | Example                                      | What it returns                                                                                                                                                                        |
| --------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `valid()`                   | `if (!relayHandle.valid()) return;`          | A usable local slot exists. Invalid keys, type conflicts, or exhausted capacity can prevent registration.                                                                              |
| `bound()`                   | `if (!relayHandle.bound()) return;`          | The slot has a runtime ID; it does not prove an active connection.                                                                                                                     |
| `snapshot()`                | `const auto state = relayHandle.snapshot();` | A copy of `value`, `hasValue`, `updatedAt` (device clock milliseconds), `origin`, `quality`, `dirty` (pending outbound state) and `revision`. Check `hasValue` before using the value. |
| `key()` (lazy wrapper only) | `Serial.println(relay.key());`               | The borrowed declaration key, even before registration.                                                                                                                                |

## Stream policies

Configure these before startup. Fluent methods return the handle. For `mode`, `offline`, `retention`, and `persist`, the typed handle also offers the Boolean `try*` variants below; use these when you need to detect configuration failure. `retention`, `persist`, and `scheduling` can invalidate a typed handle on failure; the lazy wrapper can resolve it again, so prefer a typed handle for registration checks.

| Method                                                 | Example                                                                                                                               | Behavior                                                                                                                                                                                                                       |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `mode(Mode)` / `tryMode(Mode)`                         | `temperature.mode(flova::Mode::Sample);` / `const bool ok = typed.tryMode(flova::Mode::Sample);`                                      | Choose `State` (default), `Sample` (measurement), `Command` (action) or `Event` (occurrence). Sample and Event are report-only. Here `typed` is a typed temperature handle.                                                    |
| `offline(OfflinePolicy)` / `tryOffline(OfflinePolicy)` | `temperature.offline(flova::OfflinePolicy::StoreHistory);` / `const bool ok = typed.tryOffline(flova::OfflinePolicy::StoreHistory);`  | Use `KeepLatest` (default), `StoreHistory` (bounded history), `Drop` (no offline delivery), or `Reject` (refuse the operation offline).                                                                                        |
| `scheduling(Scheduling)`                               | `relayHandle.scheduling(flova::Scheduling::CloudOnly);`                                                                               | Opt a writable stream into Console scheduling. Default `Disabled`; call before `begin()` and check `relayHandle.valid()`.                                                                                                      |
| `retention(policy)` / `tryRetention(policy)`           | `temperature.retention(history);` / `const bool ok = typed.tryRetention(history);`                                                    | Limit offline history using `HistoryRetentionPolicy`; see the example below. This does not increase physical capacity.                                                                                                         |
| `persist(policy[, intervalMs])` / `tryPersist(...)`    | `relay.persist(flova::PersistencePolicy::OnChange);` / `const bool ok = typed.tryPersist(flova::PersistencePolicy::Deferred, 30000);` | `None` (default), `Persistent`/`Immediate` (save every update), `OnChange` (skip redundant saves), or `Deferred` (save after an interval starting at the first unsaved update; defaults to 1000 ms). Requires working storage. |
| `flush()`                                              | `if (!relay.flush()) Serial.println("State not saved");`                                                                              | Try to save that stream's pending value immediately. True also means there was nothing pending. Not a Link flush.                                                                                                              |

```cpp
flova::HistoryRetentionPolicy history;
history.maximumBytes = 4096;
history.maximumRecords = 4;
history.maximumAgeSeconds = 3600;
history.minimumIntervalMs = 60000;
history.overflow = flova::HistoryOverflow::DropOldest; // or DropNewest
temperature.offline(flova::OfflinePolicy::StoreHistory).retention(history);
```

Zero in a limit field leaves that limit unset. Keep calling `run()` even offline so deferred saves can run. Persisting the latest value and storing report history are separate; see [Datastreams](../datastreams/#persistence-and-offline-history).

## `WriteResult`

Both `write()` and `report()` return `flova::WriteResult { status, reason, message }`. `accepted()` is true for `Accepted` and `NoChange`. `Rejected` means a policy, input, or hardware handler refused the operation; `Failed` means it could not complete. Use a short, stable reason code in handlers and keep any returned strings alive; do not return pointers to local arrays.

| Helper                                                          | Return from a handler when…                          | Example                                                     |
| --------------------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------- |
| `flova::accept()` / `WriteResult::accept()`                     | The action was accepted.                             | `return flova::accept();`                                   |
| `flova::unchanged()` / `WriteResult::noChange()`                | There was no hardware change to make.                | `return flova::unchanged();`                                |
| `flova::reject(reason[, message])` / `WriteResult::reject(...)` | The action was refused, for example by an interlock. | `return flova::reject("interlock", "Output is locked");`    |
| `WriteResult::failure(reason[, message])`                       | An operation could not be completed.                 | `return flova::WriteResult::failure("driver_unavailable");` |
| `accepted()`                                                    | You need to branch on either success status.         | `if (!result.accepted()) Serial.println(result.reason);`    |

### Text and color helpers

`flova::Text(const char*)` copies bounded text; oversized input produces an invalid, empty value. `valid()` checks the length result, `empty()` checks for an empty string, and `c_str()` borrows the text until the object changes or is destroyed. Typed `write()` and `report()` reject invalid text. Use `parseRgbHex(text, output)` to validate `#RRGGBB`; use `formatRgbHex(color)` to convert an `RgbColor` to uppercase hex text.

```cpp
flova::Text text("#33aaff");
flova::RgbColor color{};
if (text.valid() && !text.empty() && flova::parseRgbHex(text, color)) {
  const auto formatted = flova::formatRgbHex(color);
  Serial.println(formatted.c_str()); // #33AAFF
}
```

## Startup and runtime status

### `begin()`

Returns `bool`. Call once during startup after registering handlers and policies. A true return starts the lifecycle; it does not guarantee a connection or stream binding. With explicit `FlovaClient`, `begin(false)` (default) waits for an application handoff; `begin(true)` enables the configured managed setup path.

```cpp
started = device.begin();
if (!started) Serial.println(device.lastError()); // Arduino facade
```

### `run()`

Returns `void`. Call regularly from the same application loop that owns hardware, including while disconnected. It advances setup, reconnects, configuration, incoming commands, and outbound work. Do not call it from an interrupt or a network callback.

```cpp
void loop() {
  if (started) device.run();
}
```

### `status()` and `setStatusListener()`

Available on managed ESP, universal (including BLE), custom BLE, and `FlovaClient`. `status(output)` copies a `FlovaStatusSnapshot`, including lifecycle, readiness, maintenance, restart reason, configuration generation and error code. `setStatusListener(listener[, context])` registers a callback for changes dispatched from `run()`; events contain `kind`, `previous`, and `current`. The event is borrowed during the callback. Pass `nullptr` to stop listening.

```cpp
FlovaStatusSnapshot status{};
device.status(status);
device.setStatusListener([](void*, const FlovaStatusEvent& event) {
  if (event.kind == FlovaStatusEventKind::ReadyChanged)
    Serial.println(event.current.ready ? "Ready" : "Not ready");
});
// When your application no longer wants events:
// device.setStatusListener(nullptr);
```

### Linux OTA updater [#linux-ota-updater]

`flova_linux::OtaUpdater(root, activePath)` from `<FlovaLinux.h>` operates on files. Keep both paths on the same filesystem. The supervisor verifies the artifact source, controls restarts, and runs health checks; the updater does not replace a running process.

| Method                                                      | Example                                                                                                   | Contract                                                                                                                    |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Constructor                                                 | `flova_linux::OtaUpdater updater("/var/lib/flova/ota", "/var/lib/flova/bin/device");`                     | Set the staging directory and active executable path.                                                                       |
| `stage(sourcePath, version, expectedBytes, expectedSha256)` | `if (updater.stage(downloadPath, version, bytes, sha256) != flova_linux::OtaStageResult::Staged) return;` | Validate the version and offer, verify size and SHA-256 against trusted metadata, and stage the file. Does not activate it. |
| `activate(version)`                                         | `if (!updater.activate(version)) return;`                                                                 | Promote the staged file and retain the replaced active image. The supervisor must start the candidate and verify it.        |
| `confirm(version)`                                          | `if (healthy && !updater.confirm(version)) logConfirmationFailure();`                                     | Record the version after external health checks. The method does not perform those checks.                                  |
| `rollback()`                                                | `if (!healthy && updater.rollback()) restartService();`                                                   | Restore the retained image; the supervisor restarts it. Handle a failed rollback explicitly.                                |

## Portable runtime and adapter APIs

`core` below is a `flova::Device`. Use typed handles in ordinary application code. An adapter that already has a bound ID can use the ID-based API without creating another handle.

| Method                                                              | Example                                                                                                                                                            | Behavior                                                                                                                                                                                  |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `datastreamCount()`                                                 | `const auto slots = core.datastreamCount();`                                                                                                                       | Count allocated stream slots, not the number of bound cloud streams.                                                                                                                      |
| `storageInfo([refresh])`                                            | `const auto info = core.storageInfo(true);`                                                                                                                        | Read backend facts such as available bytes and persistence; `true` may perform expensive accounting. It does not enable storage-backed features.                                          |
| `flushPersistence()`                                                | `if (!core.flushPersistence()) return;`                                                                                                                            | Flush all dirty per-stream persistence and report whether all saves succeeded.                                                                                                            |

## Local timer API

Include `<FlovaScheduler.h>`. `flova::Scheduler(wallClock)` borrows an application `WallClock`, whose `synchronized()` reports whether time can be used and whose `localTime(timezone, output)` fills a `flova::LocalTime` or returns false. `daily(hour, minute, timezone, handler[, weekdays])` returns false for invalid input or a full table (eight entries). The optional mask uses bit 0 for Sunday through bit 6 for Saturday; default is every day. Keep the timezone string alive. `run()` calls handlers during the due minute, at most once per date per entry in RAM, with no replay of missed minutes. Re-register after reboot.

```cpp
#include <FlovaScheduler.h>

flova::Scheduler timers(wallClock); // supplied by the application
void turnOff() {
  const auto result = relay.write(false);
  if (!result.accepted()) Serial.println(result.reason);
}

// In setup(): Monday through Friday, at 20:00 local time.
// if (!timers.daily(20, 0, "IRST-3:30", turnOff, 0x3e)) return;
// In loop(): call timers.run() alongside device.run().
```

This API is separate from [Console schedules](../scheduling/#cloud-schedules).
