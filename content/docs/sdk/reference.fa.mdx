این صفحه سطح عمومی برنامه را که در راهنماها استفاده شده فهرست می‌کند. برای
امضای دقیق و Overloadهای مخصوص هر Target، Headerهای ارائه‌شده در نسخهٔ
FlovaSDK را ببینید. به Classها و Typeهای داخلی که در این صفحه نیامده‌اند
وابسته نشوید.

## Facadeهای برد

| Type | کاربرد |
| --- | --- |
| <code>FlovaEsp32</code> | برنامهٔ سفارشی ESP32 با Wi-Fi مدیریت‌شده و Flova Link. |
| <code>FlovaEsp8266</code> | برنامهٔ سفارشی ESP8266 با همان مدل Typeدار Datastream. |
| <code>FlovaUniversalEsp32</code> | ترکیب کامل ESP32 با Provisioning و رفتار Device تحت مدیریت Flova. |
| <code>FlovaUniversalEsp8266</code> | ترکیب کامل ESP8266. |
| <code>FlovaLinux</code> | Process دستگاه در Linux یا Raspberry Pi. |
| <code>flova::Device</code> | هستهٔ قابل انتقال برای برد یا Gateway سفارشی. |

## متدهای چرخهٔ اجرا

| متد | کاربرد |
| --- | --- |
| `begin()` | پس از ثبت Handlerها یک بار هنگام شروع فراخوانی کنید. موفقیت آن به معنی آنلاین شدن دستگاه نیست. |
| `run()` | حتی آفلاین هم مرتب از حلقهٔ اصلی فراخوانی کنید؛ راه‌اندازی، اتصال مجدد، پیکربندی و فرمان‌ها را پیش می‌برد. |
| <code>connected()</code> | وضعیت فعلی Connection مربوط به Transport را گزارش می‌کند. |
| `ready()` | آمادگی دستگاه برای کار عادی را نشان می‌دهد، نه رسیدن یک گزارش خاص به کنسول. |
| `lastError()` | در کلاس‌هایی که این متد را دارند، پس از خطای شروع آخرین خطا را بررسی کنید. |
| <code>datastream&lt;T&gt;(key)</code> | یک مرجع Typeدار برای Datastream می‌دهد. |
| <code>value()</code> | مقدار موجود در Cache محلی را می‌خواند. |
| <code>write(value)</code> | یک فرمان محلی از طرف برنامه را اعمال می‌کند. |
| <code>report(value)</code> | مشاهدهٔ حسگر یا وضعیت واقعی Hardware را Report می‌کند. |
| <code>onWrite(handler)</code> | Handler مرز Hardware برای فرمان راه دور را ثبت می‌کند. |

## توابع کمکی Arduino

این ماکروها شکل کوتاه متدهای نوع‌دار C++ هستند. کلید و نوع داده باید با
نوع دستگاه منتشرشده یکسان باشند. حروف بزرگ و کوچک در کلید تفاوت دارند.

| تابع کمکی | متد معادل | کاربرد |
| --- | --- | --- |
| `FLOVA_DATASTREAM(device, bool, "relay")` | `device.stream<bool>("relay")` | ارجاع دیتاستریم را بعد از شیء دستگاه تعریف کنید. تعریف سراسری به‌تنهایی دیتاستریم را ثبت نمی‌کند و به حافظهٔ ماندگار دسترسی ندارد. |
| `FLOVA_SETTING(device, double, "threshold", 35.0)` | `device.setting<double>("threshold", 35.0)` | تنظیم را با مقدار پیش‌فرض تعریف کنید. `threshold.value()` مقدار محلی را بدون درخواست شبکه می‌خواند. |
| `FLOVA_ON_WRITE(relay, setRelay)` | `relay.onWrite(setRelay)` | پیش از `begin()`، Handler سخت‌افزار را ثبت کنید. برای بررسی موفقیت ثبت، از `relay.tryOnWrite(setRelay)` استفاده کنید. |
| `FLOVA_WRITE(relay, true)` | `relay.write(true)` | تغییر محلی را از همان Handler فرمان راه دور درخواست کنید. `flova::WriteResult` را بررسی کنید. |
| `FLOVA_REPORT(temperature, 23.4f)` | `temperature.report(23.4f)` | مشاهده را بدون فراخوانی Handler گزارش کنید. پذیرش محلی به معنی تحویل نیست. |
| `FLOVA_HAS_VALUE(relay)` | `relay.hasValue()` | وجود مقدار محلی را بررسی کنید؛ مقدار می‌تواند بازیابی‌شده یا قدیمی باشد. |
| `FLOVA_READ(relay)` | `relay.value()` | مقدار محلی را بدون درخواست شبکه بخوانید. اگر نبود مقدار مهم است، ابتدا `hasValue()` را بررسی کنید. |

برای درخواست عمل از **write** و برای توصیف وضعیت مشاهده‌شده از **report**
استفاده کنید. `relay.write(false)` درخواست خاموش کردن رله است؛
`relay.report(false, flova::Origin::PhysicalInput)` گزارش این است که ورودی
بازخورد، رله را خاموش دیده است. منشأ پیش‌فرض گزارش حسگر `flova::Origin::SensorRead` است.

### ثبت Handler و بررسی شروع

برای دیتاستریم Boolean قابل‌نوشتن با کلید `led` و LED فعال با سطح بالا روی GPIO2:

```cpp
#include <Arduino.h>
#include <FlovaSDK.h>

FlovaEsp32 device;
auto led = FLOVA_DATASTREAM(device, bool, "led");
bool started = false;

flova::WriteResult setLed(bool enabled) {
  digitalWrite(2, enabled ? HIGH : LOW);
  return flova::accept();
}

void setup() {
  Serial.begin(115200);
  pinMode(2, OUTPUT);
  digitalWrite(2, LOW);
  if (!led.tryOnWrite(setLed)) {
    Serial.println("Could not register the led handler");
    return;
  }
  started = device.begin();
  if (!started) Serial.println(device.lastError());
}

void loop() {
  if (started) device.run();
}
```

اگر سخت‌افزار می‌تواند درخواست را رد کند، پیش از تغییر خروجی آن را بررسی
کنید و در صورت رد `flova::reject("reason_code")` را برگردانید. Handler را
کوتاه نگه دارید: فرمان راه دور از `run()` و فرمان محلی در خود `write()` آن
را فراخوانی می‌کند. سیاست‌های ماندگاری و آفلاین در [دیتاستریم‌ها](../datastreams/) آمده‌اند.

## نتیجه و وضعیت نوشتن

`flova::WriteResult` شامل `status`، `reason` و `message` است. `accepted()`
برای `Accepted` و `NoChange` مقدار `true` می‌دهد؛ برای تشخیص تغییر `status`
را بخوانید. `Rejected` یعنی ورودی یا Handler درخواست را رد کرده است؛
`Failed` یعنی عملیات کامل نشده است. علت را از `reason` بخوانید و فرض نکنید
درخواست ردشده سخت‌افزار یا مقدار محلی را تغییر داده است.

Typeهای عمومی مقدار شامل Boolean، <code>int64_t</code>، <code>float</code>،
<code>double</code> و متن محدود هستند. Enumهای عمومی Lifecycle و Diagnostic
در Headerهای SDK تعریف شده‌اند. به Protocolهای تولیدشده یا Classهای خصوصی
Adapter وابسته نشوید.

## متدهای وضعیت

برنامه‌های سفارشی Arduino می‌توانند بدون ورود به پیاده‌سازی Transport، مرزهای
چرخهٔ اجرا را بررسی کنند:

| متد | کاربرد |
| --- | --- |
| <code>networkConnected()</code> | Network برنامه در دسترس است. |
| <code>tlsReady()</code> | پیش‌نیازهای TLS یا Transport امن آماده هستند. |
| <code>runtimeReady()</code> | Runtime احراز هویت‌شدهٔ Flova آماده است. |
| <code>ready()</code> | Facade برای کار عادی Device آماده است. |
| <code>status(output)</code> | یک نمای لحظه‌ای محدود برای Diagnostic می‌نویسد. |
| <code>setStatusListener(...)</code> | تغییرهای Lifecycle را مشاهده می‌کند. |
| <code>startProvisioning()</code> | Session Flova را پاک و منتظر Handoff تازه می‌ماند. |
| <code>factoryReset()</code> | وضعیت خصوصی Flova را از مسیر Facade بازنشانی می‌کند. |

وضعیت برای نشانگر محصول یا صفحهٔ Maintenance مفید است، اما جای Accepted
Command یا Telemetry تازه را نمی‌گیرد.

## متدهای Firmware و توان

Facadeهای Target ممکن است این عملیات Lifecycle را ارائه کنند:

| متد | کاربرد |
| --- | --- |
| <code>setFirmwareTarget(target)</code> | شناسهٔ Target گزارش‌شدهٔ Image را تعیین می‌کند. |
| <code>enableOta(enabled)</code> | مسیر OTA مربوط به Target را فعال یا غیرفعال می‌کند. |
| <code>setOtaProfile(...)</code> | روش OTA و Boot Layout را مشخص می‌کند. |
| <code>setRestartHandler(...)</code> | اجرای Restart را به برنامه می‌سپارد. |
| <code>restartRequired()</code> | بررسی می‌کند Runtime به Restart نیاز دارد یا نه. |
| <code>prepareForPowerDown()</code> | پیش از Sleep یا قطع برق کار SDK را آرام می‌کند. |

فقط از متدهای Target انتخاب‌شده استفاده کنید. Service Supervisor در Linux،
Boot Layout در ESP32 و Staged Update در ESP8266 مرزهای مالکیت یکسانی ندارند.

## مدیریت نتیجه‌ها

~~~cpp
const flova::WriteResult result = FLOVA_REPORT(sensor, value);
if (!result.accepted()) {
  logReportFailure(result.status, result.reason);
}
~~~

نتیجهٔ Accepted یعنی SDK عملیات را در مرز خودش پذیرفته است. در MQTT همچنان
<code>run()</code> را اجرا کنید و Latest Value یا History را در Console
بررسی کنید. در نوشتن Hardware، Accepted باید به معنی پذیرفته شدن وضعیت واقعی
توسط Handler محصول باشد.

## تغییرات 0.5.0

کلاس‌های استاندارد ESP اکنون راه‌اندازی و Wi-Fi را مدیریت می‌کنند. اگر
شبکه با برنامه است از `FlovaClient` استفاده کنید، نه سازنده‌های قدیمی
PubSubClient یا `attachProvisioning()`. برای تعویض Wi-Fi مدیریت‌شده،
`startWifiSetup()`، `wifiSetupActive()`، `wifiSetupError()` و
`cancelWifiSetup()` در [راهنمای Provisioning](../provisioning/) توضیح داده شده‌اند.

تا وقتی به Constructor یا متد مخصوص Target نیاز ندارید، Header عمومی
<code>&lt;FlovaSDK.h&gt;</code> را ترجیح دهید.
