## Definition of streams
```cpp
auto relay = client.datastream<bool>("relay");
auto temperature = client.datastream<float>("temperature");
auto label = client.datastream<flova::Text>("label");
```
For custom code, shorter helpers call the same typed API:

| Helper | Meaning |
| --- | --- |
| `FLOVA_DATASTREAM(client, type, key)` | Creating a typed stream
| `FLOVA_WRITE(stream, value)` | local write from the path handler |
| `FLOVA_READ(stream)` | Read cache without network request
| `FLOVA_REPORT(stream, value, ...)` | Report the observed value
| `FLOVA_ON_WRITE(stream, handler)` | Register the command handler
| `FLOVA_HAS_VALUE(stream)` | Checking the existence of the value in the cache

These helpers do not replace the typed contract API; Type, mode, behavior and key must
be equal to Device Type.

For numeric values, record the unit and range in Device Type. SDK itself is not supposed to
guess the meaning of `temperature` or `relay`; The product contract is defined in Console
And the firmware implements the same contract with the exact name and type.

## Get command with `onWrite`

The remote or local command must pass through the handler of the same stream. handler for
Write the actual hardware change and keep the operation result clear:
```cpp
relay.onWrite([](bool enabled) {
  digitalWrite(RELAY_PIN, enabled ? HIGH : LOW);
  return flova::WriteResult::accept();
});
```
If the hardware cannot apply the value, do not declare it as accepted:
```cpp
relay.onWrite([](bool enabled) {
  if (!setRelay(enabled)) {
    return flova::WriteResult::reject("relay is unavailable");
  }
  return flova::WriteResult::accept();
});
```
In the real application, keep the callback short. Long tasks like waiting for
Don't put the network or do some heavy steps in it; The main loop should have a chance to execute
`client.run()` and handle the connection.

## Control an RGB LED

In Console, the "RGB color mode" option is a non-base datastream with type `object`.
Makes behavior `state` and access `read_write`. Studio Color as a value
`{r,g,b}` writes with valid channels 0 to 255. Device Link the same value as the text
`#RRGGBB` to firmware; In SDK you should register it as `flova::Text`.
```cpp
auto lamp = client.datastream<flova::Text>("lamp_color");

flova::WriteResult applyColor(flova::Text value) {
  flova::RgbColor color;
  if (!flova::parseRgbHex(value, color))
    return flova::reject("invalid_color");

  // Pin numbers and polarity depend on your circuit; invert the example for a common anode LED.
  analogWrite(RED_PIN, color.r);
  analogWrite(GREEN_PIN, color.g);
  analogWrite(BLUE_PIN, color.b);
  return flova::accept();
}

// In setup, before client.begin():
lamp.onWrite(applyColor);

// If the color changes on the device:
flova::RgbColor localColor = {255, 128, 0};
lamp.report(flova::formatRgbHex(localColor));
```
Full examples of ESP32 and ESP8266 in `examples/datastream-api-esp32` and
`examples/datastream-api-esp8266` are the firmware repository. Optimum value in Engine
It is kept and returned to the device after connecting. Callback acceptance ie
The color application code is executed; You need to reread the hardware to ensure real light
and report with `report`. Universal Firmware guesses from a three-pin PWM color
It doesn't work and needs the device code.

## Report sensor value with `report`

`report` is for announcing new observations of hardware. For example, after reading the sensor:
```cpp
temperature.report(readTemperature());
```
This action is not a command to the hardware. If the value of the sensor has not changed, it is not necessary for no reason
Send it in each round of the loop; Sampling interval with product and consumption needs
Adjust energy.

## Read cache with `value`
```cpp
bool currentRelay = relay.value();
float currentTemperature = temperature.value();
```
`value()` returns a locally known value and is suitable for immediate reading. that
Do not treat as a fresh request from the device or a connection guarantee. for decisions
Importantly, consider the connection status and the result of the last operation in the UI or automation design.

## Offline mode

The device may be temporarily offline. firmware must be able to local logic and
Keep the last value of the hardware as much as possible and enter the cycle again after the connection is restored
become normal In Universal Firmware, this section is coordinated with the platform runtime; in
Custom firmware is responsible for safe offline behavior with your app.

Answer these questions for each stream:

- If the last command does not reach the device, what state should the output be in?
- If the sensor is not read for a while, what should dashboard show?
- Is it safe to re-execute a command?

## Suggested execution cycle

The typical pattern of the program is as follows:
```cpp
void loop() {
  client.run();

  if (millis() - lastSample > SAMPLE_INTERVAL) {
    lastSample = millis();
    temperature.report(readTemperature());
  }
}
```
On a board that has special hardware, `readTemperature` and `setRelay` with the driver
Implement the same board. The datastream contract remains fixed and the rest of Flova is not required
Know whether the sensor comes from I2C or ADC or a ready module.
