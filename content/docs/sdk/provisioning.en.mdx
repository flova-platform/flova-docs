Provisioning connects a physical unit to a Flova device record. It supplies a
short-lived handoff, then the device receives or creates the runtime identity it
stores for later boots.

## Universal firmware

Universal ESP32 and ESP8266 firmware includes a setup path. The user completes
the setup flow, the device receives its network and Flova handoff, and the
firmware stores the resulting runtime state. Later boots restore the stored
identity and connect without repeating the first-boot flow.

## Custom applications

With `FlovaEsp32` or `FlovaEsp8266`, the SDK manages Wi-Fi and SoftAP setup;
the sketch owns GPIO and application behavior. Start device setup in Flova,
join `Flova-Setup-*` when prompted, and open the link supplied by Flova. Opening
`/setup` directly does not complete first-time provisioning. Once the device
accepts setup, return to the internet and verify that it comes online.

The setup network is open by default. For production use a device-unique
8–63-character WPA password. ESP32 BLE variants require a device-unique proof
of possession; do not enable unauthenticated BLE setup in production.

The handoff contains the deployment's Link URL and a short-lived token. The
device uses it to bootstrap and stores the resulting session. Do not commit
tokens, device secrets, Wi-Fi passwords, or complete provisioning payloads.

## A custom provisioning channel

The same model works for a factory tool, serial adapter, BLE flow, or Ethernet
setup path:

```cpp
flova::ProvisioningHandoff handoff(linkUrl, shortLivedToken);
client.provision(handoff);
```

The channel owns its input and transport. The SDK owns the bounded handoff and
the Flova session lifecycle. Network credentials remain with the application or
the selected universal composition.

## Factory reset

Use [`factoryReset()`](../reference/#provisioning-and-wi-fi) when the product needs
to clear Flova state and restart. On managed Wi-Fi targets this also clears
managed network credentials. The application still owns unrelated product data.

After provisioning, verify the device in Console. Check its online status,
template, firmware target, and first datastream report separately.

## What provisioning stores

The completed handoff results in a Flova session containing the device identity,
organization and template association, Link URL, and runtime secret. The SDK
stores the session through the selected storage service. Your application should
not copy that secret into a second configuration file or expose it through a
status page.

The activation token is a bootstrap input. It is not the runtime password and
should not be sent on every boot. After the session is committed, later boots
restore the session and authenticate with the stored runtime identity.

## Provisioning states

Treat setup as a state machine rather than a single HTTP request:

| State | Application behavior |
| --- | --- |
| Waiting | Keep the setup channel available and run the SDK normally. |
| Bootstrapping | Continue polling from the normal loop; do not start another session. |
| Committing | Keep power and storage available until the session is durable. |
| Ready | Close temporary setup resources and start normal device operation. |
| Failed | Show a bounded error, keep recovery available, and retry deliberately. |

The exact status names differ between facades, but the boundaries are the same.
Do not treat a submitted form as proof that the device is ready. Confirm the
stored session, authenticated Link connection, template binding, and first
accepted report.

## Application-owned web setup

If your application owns Wi-Fi, a web server, or an alternate setup channel,
compose `FlovaClient` explicitly. The following ESP32 fragments fit into an existing
application; they are not a standalone web server.

```cpp
#include <FlovaSDK.h>

FlovaEsp32ObservedNetwork network;

FlovaEsp32Storage storage;

ArduinoFlovaLogger logger;
ArduinoFlovaManualHardware hardware;

FlovaClient client(flovaLink, provisioning, network, tlsClock, identity, storage,
                   clockSource, logger, entropy, hardware);
```

In `setup()`, start Wi-Fi using your existing application code and register
any datastream handlers. Call `client.begin(false)` and check the result. In
`loop()`, service the web server and call `client.run()` regularly. An
unprovisioned device can now wait for a handoff on your setup channel.

## Replace Wi-Fi without resetting identity

On a provisioned managed ESP32 or ESP8266, trigger `startWifiSetup()` from the
normal board loop and keep calling `run()`. A true return means the request was
accepted, not that the new network works. Busy configuration, OTA, or command
processing can reject the request. After setup becomes active, join the setup
network and open `http://192.168.4.1/setup`. No activation token is needed.

Use `wifiSetupActive()` and `wifiSetupError()` to inspect progress, or
`cancelWifiSetup()` to return to the previous network. The device tests Wi-Fi
association for up to 30 seconds; association does not prove internet access.
Failed candidates leave saved credentials intact. An ordinary outage does not
open setup or erase credentials. Confirm the device comes back online before
leaving the installation.

## Recovery and reset

Use `startProvisioning()` to replace the Flova identity, or `factoryReset()`
when the user intends to reset the device. Define the action clearly, such as a
physical button hold or an authenticated maintenance command, and tell the user
which data will be cleared. See the [API reference](../reference/#provisioning-and-wi-fi) for the difference.

If bootstrap fails, check the setup channel, Link URL, token lifetime,
clock readiness, storage availability, and device claim separately. Keep error
messages bounded and never include the token or secret.
